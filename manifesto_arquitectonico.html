Manifiesto Arquitectónico: TravelHub

Fecha: 02 de junio de 2026

Autor: The Architect

Este documento no es una crítica, es una hoja de ruta. Es el plan para elevar TravelHub de un proyecto funcional y complejo a un sistema de ingeniería de clase mundial, resiliente, escalable y preparado para dominar su mercado. La complacencia es el enemigo del crecimiento. Aquí es donde empezamos a forjar la excelencia.

1. Arquitectura Actual (El "As-Is"): El Monolito Modular

La arquitectura actual es un "Monolito Modular". Has evitado el anti-patrón de un `core` gigante y has organizado la lógica de negocio en módulos de dominio (`apps/*`). Esto es loable. Sin embargo, la modularidad es una ilusión si el acoplamiento y las dependencias no se gestionan con una disciplina de hierro. El sistema actual sufre de tres debilidades estructurales clave.

Debilidad 1: Tenencia Implícita - El Corazón Frágil

El sistema se apoya en ThreadLocalContextMiddleware para gestionar el multi-tenancy. Esto es un estado global implícito, una forma de "magia" que es conveniente en la superficie pero extremadamente peligrosa en la práctica.

Evidencia (core/middleware_saas.py):

# El middleware depende de que otro middleware anterior 
# haya inyectado 'agencia' en el objeto request.
agencia = getattr(request, 'agencia', getattr(request, 'agency', None))

if agencia:
    # ...lógica de cuotas...

Evidencia (apps/bookings/tasks.py):

@shared_task(queue="notifications")
def notificar_pago_whatsapp_task(venta_id, agencia_id=None):
    # ...
    try:
        # El desarrollador DEBE recordar pasar agencia_id. Si es None, se rompe la tenencia.
        if agencia_id:
            agencia = Agencia.objects.get(pk=agencia_id)
            ctx = agency_context(agencia) # Se necesita un contexto manual
        else:
            ctx = system_context() # ¿Qué es esto? ¿Opera sin tenencia? Peligroso.

        with ctx: # Bloque 'with' manual en cada tarea. Propenso a olvidos.
            # ... lógica de la tarea ...
    except Exception as e:
        # ...

Impacto: Un solo olvido al llamar una tarea Celery, un middleware que falle, o una futura migración a ASGI, y el sistema colapsará, mezclando datos de clientes. Es el riesgo existencial número uno para un SaaS.

Debilidad 2: Acoplamiento Directo - El Monolito Distribuido

Los módulos de dominio se importan entre sí directamente. Esto significa que no son módulos, son simplemente carpetas. Has creado un monolito donde las dependencias, en lugar de estar en un solo lugar, están escondidas y distribuidas, lo cual es peor.

Evidencia (apps/bookings/services/venta_service.py):

class VentaService:
    @staticmethod
    def recalculate_finances(venta_id):
        try:
            # ¡Alerta Roja! bookings conoce y depende directamente de la implementación de finance.
            from apps.finance.services.finance_service import FinanceService
            FinanceService.recalculate_sale_finances(venta_id)
        except Exception as e:
            # ...

Impacto: No se puede probar, desplegar o refactorizar `bookings` sin `finance`. Un cambio en `finance` puede romper `bookings` de formas inesperadas. La velocidad de desarrollo se desploma a medida que el grafo de dependencias se enmaraña.

Debilidad 3: El Kernel `core` - El Sol Centralizado

Aunque no es un "agujero negro", el `core` se ha convertido en el "sol" de tu sistema. Todo gira en torno a él. Todas las apps de dominio tienen una dependencia dura con su implementación interna.

Evidencia (travelhub/settings.py):

INSTALLED_APPS = [
    # ...
    'core.apps.CoreConfig', # Módulo Núcleo
    'apps.bookings.apps.BookingsConfig',
    'apps.finance.apps.FinanceConfig',
    # ... 8 más ...
]

MIDDLEWARE = [
    # ...
    'core.middleware.MultiTenantDomainMiddleware',
    'core.middleware.ThreadLocalContextMiddleware',
    # ... y 5 más de 'core' ...
]

Impacto: El `core` es un cuello de botella. Un cambio en un modelo o servicio del `core` requiere volver a probar todo el sistema. Las apps de dominio no son reutilizables ni independientes. Si quisieras extraer `apps/crm` para otro proyecto, no podrías, porque está fusionado con el `core` de TravelHub.

2. Arquitectura Objetivo (El "North Star"): Desacoplamiento y Resiliencia

La arquitectura de élite no es sobre añadir más tecnología, es sobre eliminar dependencias y hacer que las interacciones sean explícitas y controladas. Nuestra visión se basa en tres principios:

Principio 1: Tenencia Explícita y Obligatoria

La tenencia no es opcional. Se pasa como un parámetro de primer nivel. No hay magia.

# tasks.py refactorizado
# Nota: 'agencia_id' ya no es opcional. Falla rápido si no se provee.
@shared_task(queue="notifications")
def notificar_pago_whatsapp_task(venta_id, agencia_id):
    # Ya no hay 'with'. El contexto se maneja a nivel de query.
    from core.models import Agencia
    agencia = Agencia.objects.get(pk=agencia_id)
    
    # Cada query es explícitamente para esa agencia.
    venta = Venta.objects.get(pk=venta_id, agencia_id=agencia_id)
    
    # ...lógica...
    send_whatsapp_message(..., agencia=agencia)

Principio 2: Comunicación Asíncrona por Eventos

Los módulos no se llaman entre sí. Emiten eventos. "Venta creada". "Pago recibido". Otros módulos se suscriben a estos eventos y reaccionan. Usaremos las señales de Django como primer paso.

# apps/bookings/services/venta_service.py (Refactorizado)
from core.events import sale_recalculation_requested

class VentaService:
    @staticmethod
    def recalculate_finances(venta_id, agencia_id):
        # bookings ya no sabe de 'finance'. Solo emite un evento.
        sale_recalculation_requested.send(
            sender=Venta, 
            venta_id=venta_id, 
            agencia_id=agencia_id
        )

# apps/finance/receivers.py (Nuevo archivo)
from django.dispatch import receiver
from core.events import sale_recalculation_requested
from .services.finance_service import FinanceService

@receiver(sale_recalculation_requested)
def handle_sale_recalculation(sender, **kwargs):
    # Finance reacciona al evento.
    venta_id = kwargs['venta_id']
    FinanceService.recalculate_sale_finances(venta_id)

Principio 3: El Kernel como un Framework

El `core` no es una app, es un framework interno. Provee herramientas (ej. un `TenantAwareModel` base, un `TenantAwareManager`), pero no dicta la lógica de negocio. Las apps de dominio usan estas herramientas, pero no dependen de la implementación interna del `core`.

3. El Plan de Migración: Evolución sin Apocalipsis

Un "Big Bang" es una sentencia de muerte. La migración se hará de forma incremental, segura y sin detener el desarrollo actual. Cada fase debe ser pequeña y aportar valor.

Preparación y Cimientos

Objetivo: Preparar el terreno sin cambiar código de producción.

  1. Crear un Linter de Dependencias: Implementar un script de pre-commit que falle si detecta una importación directa entre módulos de `apps/` (ej. `from apps.finance...` dentro de `apps/bookings`). Esto previene que la deuda técnica aumente.
  2. Definir las Señales Centrales: Crear un archivo `core/events.py` y definir las 2-3 señales más importantes (ej. `venta_creada`, `pago_recibido`).
  3. Crear `TenantAwareManager`: Crear un manager de modelo personalizado en `core` que automáticamente filtre por la agencia activa. `objects = TenantAwareManager()`. Esto ayudará en la Fase 2.

Erradicar la Tenencia Implícita

Objetivo: Hacer la tenencia explícita en todo el sistema, empezando por las tareas asíncronas.

  1. Crear `TenantAwareTask`: Definir una clase base para Celery en `core/celery.py` que sobreescriba `__call__`. Esta tarea base requerirá `agencia_id` como argumento y lo usará para configurar el contexto de forma segura y automática, eliminando la necesidad de los bloques `with ctx:`.
  2. Refactorización Incremental:
    • Cambia una sola tarea para que herede de `TenantAwareTask`.
    • Modifica su firma para que `agencia_id` sea obligatorio.
    • Encuentra todas las llamadas a esa tarea (`.delay()`) y añade el `agencia_id`.
    • Prueba exhaustivamente. Repite con la siguiente tarea.
  3. Refactorizar Vistas: Una vez que las tareas estén seguras, empieza a pasar el objeto `agencia` explícitamente a las funciones de servicio en lugar de depender de que ellas lo obtengan del `thread-local`.

Romper el Acoplamiento (Dominio por Dominio)

Objetivo: Desacoplar `bookings` de `finance` usando señales.

  1. Implementar el Receiver: Crea el archivo `apps/finance/receivers.py` y añade la función `handle_sale_recalculation` que escucha la señal `sale_recalculation_requested`.
  2. Cambiar la Llamada por la Señal: En `apps/bookings/services/venta_service.py`, comenta la importación directa y la llamada a `FinanceService`. En su lugar, añade la línea `sale_recalculation_requested.send(...)`.
  3. Desplegar y Monitorear: Despliega este cambio. El comportamiento funcional es el mismo, pero la arquitectura ha mejorado radicalmente. El riesgo es bajo porque es un cambio muy localizado.
  4. Repetir: Identifica la siguiente dependencia más crítica (ej. `crm` y `bookings`) y repite el proceso.

Formalizar el API del Kernel

Objetivo: Convertir el `core` en un verdadero framework interno.

  1. Crear `core/api.py` o `core/services.py`: Centraliza las funciones que las apps de dominio necesitan del `core` (ej. `get_agency_from_request`, `get_tenant_aware_cache`). Estas funciones serán el único punto de entrada público al `core`.
  2. Deprecar Importaciones Directas: Usando el linter, empieza a prohibir importaciones a modelos o funciones internas del `core`. Fuerza a los desarrolladores a usar el API formal.
  3. Refactorizar Modelos: Crea un `core.models.TenantAwareModelBase` que todos los modelos con tenencia deben heredar. Este modelo base puede añadir automáticamente el campo `agencia` y usar el `TenantAwareManager`.

Este es un trabajo de disciplina y visión. No es fácil, pero es el camino que toman los sistemas construidos para durar y dominar. Cada paso en esta dirección no solo reduce la deuda técnica, sino que aumenta la velocidad, la seguridad y la capacidad de innovación de TravelHub. Manos a la obra.
